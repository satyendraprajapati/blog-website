---

The slowest part of building a data deck usually isn't the analysis — it's the review cycle where three stakeholders each email back a different opinion on a chart you already changed twice. PowerPoint has built-in tools for this that most analysts never turn on.

**1. Store the deck somewhere co-authoring actually works.** Comments and live version tracking only function properly when the file lives in OneDrive or SharePoint — a copy sitting in a local Downloads folder attached to five different emails guarantees five different versions with no way to merge them back together. Save the deck there first, then share a link instead of the file itself.

**2. Use slide-level and object-level comments instead of "can you check slide 7."** Select a chart, a text box, or just click on empty slide space, then insert a comment (Review tab → New Comment, or right-click → *Comment*). Anchoring the comment to the specific object means "this number looks off" points at the actual number, not a slide a reviewer has to hunt through to find what you meant.

**3. Resolve comments instead of deleting them.** Deleting a comment once you've addressed it destroys the record of what was raised and fixed — useful if a stakeholder later asks "did we account for the Q2 restatement?" Click *Resolve* instead, which greys the thread out but keeps it in the file, re-openable if the same question comes back up.

**4. Reply in-thread rather than starting a new comment.** A reply keeps the back-and-forth attached to the original point instead of scattering related feedback across six unconnected comment bubbles on the same slide — makes the eventual "who asked for this change and why" question answerable months later.

**5. Use Version History instead of a "v2," "v3," "v3_final" filename chain.** In OneDrive or SharePoint, *File → Info → Version History* shows every autosaved version with a timestamp and, when co-authoring, who made each change. If a reviewer's "simplify this chart" edit turns out to have removed a data point you needed, you can open the prior version and restore just what you need instead of reconstructing it from memory.

**6. Set expectations about what comments don't replace.** Comments are good for pointing at something specific on a slide; they're a poor place for "can we restructure the whole narrative of section 2." For a change that big, propose it as a short written summary or a quick call — a wall of nested slide comments is a bad medium for redesigning a deck's argument, even though it's a great medium for polishing one.

None of this requires a new tool or a shared drive migration — it's mostly turning on features already sitting in the Review tab, which is usually enough to turn a five-email review cycle into a single shared file with a clean, resolvable history of who asked for what.
